## Evidence and priorities

A confirmed issue requires a valid input/event trace through a real entry point and an observable contract violation, with a deterministic regression where executable. Source-proven reachability is recorded separately from tested behavior. Hypotheses are not promoted by reviewer agreement. P1 means broken execution, corruption, nontermination or repeated side effects; P2 means recoverable incorrect state/output or lifecycle leaks; P3 means lower-impact inconsistencies. Severity follows actual consequences, not the mere presence of a race.

The inventory, transition tables, grouped issue records, module dispositions and review/check results below are maintained as implementation proceeds. The final model describes supported behavior, including explicit limitations, rather than implying arbitrary concurrent library calls are supported.

### Supported concurrency and retry boundaries

The parallel scheduler owns graph synchronization; workers have independent mutable execution resources and merge cache state under `cache_mutex`. Server execution admission owns run replacement; socket writers and client collection have their own locks; confirmation wait uses its condition mutex. Sequential executors/parsers/import resolvers/watchers are single-owner objects, not generally thread-safe shared objects. A retry may rerun successful external effects from an earlier failed recipe; Jake does not promise exactly-once external side effects. Cancellation cannot undo already completed shell effects.

### Import and upgrade failure boundaries

Import resolution mutates its target AST during merging. Failures before merge (for example, a missing import that is created before retry) clean up active-stack state and can be retried with the same resolver. Allocation failure after partial merge requires discarding/deinitializing the target rather than treating it as a rolled-back transaction. The sweep does not introduce a general transactional-merge guarantee.

Upgrade is a separate staged-file lifecycle: select release → download candidate → verify when available unless explicitly skipped → install replacement → release temporary storage. Live release downloads and replacing the developer's installed executable are excluded from validation. Local file tests exercise replacement/recovery logic; Windows replacement behavior simulated through the helper is distinguished from native Windows execution.

| Upgrade state | Event / guard | Next state / owned resources | Failure invariant |
| --- | --- | --- | --- |
| Installed | Chosen release requires upgrade | Downloading a unique candidate beside the installed binary | Existing installation stays intact; staging on the same filesystem permits rename-based installation. |
| Candidate downloaded | Verification enabled and checksum available | Verified candidate or checksum failure | Mismatch rejects candidate; verification can explicitly be skipped or unavailable, matching existing policy. |
| Ready to install, POSIX | Rename candidate over installed path | New installation | Rename failure leaves previous installation; temporary candidate is cleaned. |
| Ready to install, Windows | Rename installed file to backup, then candidate into installed path | New installation plus backup | If the second move fails, restore original path; if restore itself fails, retain backup for recovery. |
| Any pre-install failure | Abort / error | Previous installation plus no live candidate | Temporary candidate has one cleanup owner; an error must not erase the only recoverable executable. |
