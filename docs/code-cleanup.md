## Evidence and priorities

A confirmed issue requires a valid input/event trace through a real entry point and an observable contract violation, with a deterministic regression where executable. Source-proven reachability is recorded separately from tested behavior. Hypotheses are not promoted by reviewer agreement. P1 means broken execution, corruption, nontermination or repeated side effects; P2 means recoverable incorrect state/output or lifecycle leaks; P3 means lower-impact inconsistencies. Severity follows actual consequences, not the mere presence of a race.

The inventory, transition tables, grouped issue records, module dispositions and review/check results below are maintained as implementation proceeds. The final model describes supported behavior, including explicit limitations, rather than implying arbitrary concurrent library calls are supported.

### Supported concurrency and retry boundaries

The parallel scheduler owns graph synchronization; workers have independent mutable execution resources and merge cache state under `cache_mutex`. Server execution admission owns run replacement; socket writers and client collection have their own locks; confirmation wait uses its condition mutex. Sequential executors/parsers/import resolvers/watchers are single-owner objects, not generally thread-safe shared objects. A retry may rerun successful external effects from an earlier failed recipe; Jake does not promise exactly-once external side effects. Cancellation cannot undo already completed shell effects.

### Import and upgrade failure boundaries

Import resolution mutates its target AST during merging. Failures before merge (for example, a missing import that is created before retry) clean up active-stack state and can be retried with the same resolver. Allocation failure after partial merge requires discarding/deinitializing the target rather than treating it as a rolled-back transaction. The sweep does not introduce a general transactional-merge guarantee.

Upgrade is a separate staged-file lifecycle: select release → download candidate → verify when available unless explicitly skipped → install replacement → release temporary storage. Live release downloads and replacing the developer's installed executable are excluded from validation. Local file tests exercise replacement/recovery logic; Windows replacement behavior simulated through the helper is distinguished from native Windows execution.

| Upgrade state | Event / guard | Next state / owned resources | Failure invariant |
| --- | --- | --- | --- |
| Installed | Chosen release requires upgrade | Downloading a unique candidate beside the installed binary | Existing installation stays intact; staging on the same filesystem permits rename-based installation. |
| Candidate downloaded | Verification enabled and checksum available | Verified candidate or checksum failure | Mismatch rejects candidate; verification can explicitly be skipped or unavailable, matching existing policy. |
| Ready to install, POSIX | Rename candidate over installed path | New installation | Rename failure leaves previous installation; temporary candidate is cleaned. |
| Ready to install, Windows | Rename installed file to backup, then candidate into installed path | New installation plus backup | If the second move fails, restore original path; if restore itself fails, retain backup for recovery. |
| Any pre-install failure | Abort / error | Previous installation plus no live candidate | Temporary candidate has one cleanup owner; an error must not erase the only recoverable executable. |

### Cache publication states after the challenge repairs

Cache entries acknowledge a particular **consumer** (file recipe or `@cache` block), not merely that some other recipe has seen the same input. A block identity includes its recipe and directive position. Signatures cover declared input content and glob membership; legacy entries without these scoped records rebuild conservatively.

| State / event | Transition and invariant |
| --- | --- |
| No committed scoped fingerprint / changed content or membership | Consumer is stale. Another target's matching fingerprint cannot satisfy this consumer. |
| Protected work about to start | Capture declared input fingerprints before the protected body/block reads them (file-target capture follows pre-hooks); hold them as pending recipe-owned state. |
| Body or later command fails / cancellation occurs during post-hook | Discard pending fingerprints. Retrying the failed/cancelled recipe must execute its protected work again. |
| Entire body succeeds and post-hook/cancellation policy permits success | Publish the captured fingerprints, not a re-read of inputs after work. Output metadata can be recorded after output creation. |
| Input is edited while output is being built | The captured old fingerprint remains different from the current input; the next invocation rebuilds rather than certifying the stale output as fresh. |
| Glob input added or removed | Membership fingerprint changes even when all surviving files are unchanged. |

These are declared-input build semantics, not hermetic filesystem snapshots or exactly-once shell execution. Arbitrary transient/ABA input rewrites, undeclared environmental inputs, and externally modified output contents are not fully isolated. Cache persistence/merge remains best-effort/nontransactional; crash or OOM may cause extra rebuilding. Checking content on every lookup adds input I/O; no performance improvement is claimed.

The parallel executor's serial/dry-run mode uses topological execution without recording every private node's threaded terminal state. The `pending → ready → running → completed/failed` table describes worker-scheduled mode; both modes reset scheduling eligibility before a new attempt.

### Attempt admission and unavailable inputs

A certificate represents the current consumer artifact, not merely a historical successful input version. Real work retires the old consumer certificate before it can alter output; failure or cancellation carries untrusted markers through worker→graph→runtime. Before mutable recipe work the old persisted cache is removed, so CLI failure via immediate process exit or interruption cannot revive that file on restart. Normal cleanup saves the current trustworthy/unavailable records. Failed/interrupted work can therefore cause conservative rebuilding. If old metadata cannot be invalidated, work aborts with a cache error before commands run.

Unavailable input snapshots are persisted explicitly and remain stale, including after byte-identical files reappear. Snapshot allocation failure aborts protected work instead of silently retaining a previous certificate. Fork dirty bits are per-entry runtime metadata; existing-key invalidation/publication does not allocate, and those bits are cleared when taking a new read snapshot. They are not serialized.

Dry-run is a separate non-mutating execution mode: commands render, but consumer certificates are not staged, retired or published. `node tests/cache_lifecycle_test.js` exercises eight real-CLI scenarios across file targets/`@cache`, sequential/parallel, and dry-run/failed-body retries. The baseline binary fails; the repaired binary passes. CI runs this POSIX fixture on Linux/macOS; Windows explicitly skips it.
